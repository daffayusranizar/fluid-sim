# T-027 Understanding — GPU Density & Pressure Kernels

Explain each snippet in your own words. Focus on **why** each choice was made and what breaks without it.

> **The TASKS.md Guide for this task is stale.** It says to port the 2D Poly6 kernel and a single Tait EOS with a hardcoded `max(0, p)`. That describes the solver as it was before the two-channel revision. What is actually ported here is SpikyPow2 + SpikyPow3 density, two pressure channels, and a clamp that is a flag. ## Snippet 1 — Two kernels, mirroring the CPU's two jobs

```hlsl
#pragma kernel ProbeRoundTrip
#pragma kernel ComputeDensity
#pragma kernel ComputePressure
```

```csharp
shader.SetBuffer(densityKernel, "_ParticlesIn", particlesIn);
shader.SetBuffer(densityKernel, "_Density", density);
shader.SetBuffer(densityKernel, "_NearDensity", nearDensity);
shader.Dispatch(densityKernel, GroupCount(), 1, 1);

shader.SetBuffer(pressureKernel, "_Density", density);
shader.SetBuffer(pressureKernel, "_Pressure", pressure);
shader.Dispatch(pressureKernel, GroupCount(), 1, 1);
```

**Explain:**
- The CPU has `ComputeDensityJob` and `ComputePressureJob` as separate jobs. Why is the GPU split the same way, rather than fused into one kernel that computes density and then immediately pressure for that particle?
- What is the dependency between the two dispatches, and how is it expressed here? On the CPU it was a `JobHandle`; what plays that role on the GPU?
- Two dispatches instead of one costs a second full pass over N particles. What does that buy when something is wrong?
- If density is correct but pressure is wrong, which of the two kernels do you fix? What if pressure *looks* plausible but density was already wrong?
- `SetBuffer` is per-kernel, while `SetFloat` is per-shader. Which uniform calls therefore have to be repeated for each kernel, and which do not?

## Snippet 2 — Brute force, deliberately

```hlsl
for (uint j = 0; j < _ParticleCount; j++)
{
    if (j == i) continue;

    float r = distance(_ParticlesIn[j].position, posI);

    mainDensity += _ParticleMass * SpikyPow2Kernel(r, _SmoothingLength, _SpikyPow2Const);
    near += _ParticleMass * SpikyPow3Kernel(r, _SmoothingLength, _SpikyPow3Const);
}
```

> *"The kernels are O(N^2): every thread loops every particle. That is deliberate at this stage. A uniform grid on the GPU needs a count sort and prefix scan, which is T-030/T-031, and doing it here would mean debugging hashing and kernel math at the same time."*

**Explain:**
- The CPU's density pass only visits neighbours inside the grid. Why does brute force still produce the **same numbers**, not merely similar ones?
- Where does the "only neighbours matter" pruning actually happen in the brute-force version? Name the line that does it.
- The CPU's grid applies `distancesq < radiusSq` as its inclusion test, while this loop computes `distance` for every `j` and relies on the kernel to return zero. Give a case where the two differ in cost but not in result.
- For N = 400 there are 160,000 kernel evaluations per pass. What is it at N = 5000, and why is that number the reason T-030/T-031 exist?
- Why is "debug one thing at a time" a correctness argument here, not just a preference?

## Snippet 3 — The boundary contribution

```hlsl
if (_UseBoundaryParticles != 0)
{
    for (uint b = 0; b < _BoundaryCount; b++)
    {
        float r = distance(_BoundaryPositions[b], posI);

        mainDensity += _RestDensity * _BoundaryVolume
                       * SpikyPow2Kernel(r, _SmoothingLength, _SpikyPow2Const);
    }
}
```

**Explain:**
- Note what is missing from this term compared with the fluid loop: no `_ParticleMass`, and `_RestDensity` instead. Why is the boundary's contribution weighted that way?
- Boundary particles are added to the **main** channel only, never to `_NearDensity`. What would adding them to the near channel do to wall behaviour, given that the near channel is always repulsive?
- What exactly goes wrong near a wall without this term? Trace it: density → pressure → force → particle behaviour. Which earlier task fixed this bug on the CPU?
- The loop is guarded by a flag, and the buffer always holds at least one parked element at `(1e9, 1e9)`. Why have both — why not rely on the parked element alone, or on the flag alone?
- Why is the boundary loop *not* inside the `j` loop?

## Snippet 4 — Two channels, and where Poly6 went

```hlsl
float SpikyPow2Kernel(float r, float h, float k)
{
    if (r >= h) return 0.0;
    float hr = h - r;
    return k * hr * hr;
}

float SpikyPow3Kernel(float r, float h, float k)
{
    if (r >= h) return 0.0;
    float hr = h - r;
    return k * hr * hr * hr;
}
```

**Explain:**
- The stale Guide says Poly6. Where is Poly6 used in the *current* CPU solver, and why can it not be used for density any more?
- Main density uses `(h - r)^2`; near density uses `(h - r)^3`. The corresponding **force** gradients are `(h - r)` and `(h - r)^2`. Why must the force gradients differ in shape, not just in a constant multiplier?
- A particle sits exactly at `r = h`. What does each kernel return, and why does that make the `r >= h` early-out load-bearing for correctness rather than an optimisation?
- `_RestDensity` multiplies the boundary term but not the fluid term; `_ParticleMass` multiplies the fluid term but not the boundary term. Explain the units on both sides.
- The invariant table says the fluid settles ~1% below `restDensity` **by design**. Which of these two kernels causes that, and which one stops the result from collapsing?

## Snippet 5 — The clamp is a flag, not a constant

```hlsl
float TaitPressure(float density, bool clampPositive)
{
    float p = _Stiffness * (density - _RestDensity);
    if (clampPositive && p < 0.0) p = 0.0;
    return p;
}
```

```csharp
shader.SetInt("_ClampPressurePositive", parameters.clampPressurePositive ? 1 : 0);
```

**Explain:**
- The Guide says to port `p = max(0, p)` because "it is deliberate". The flag defaults to **false**. Reconcile those two statements — under what condition is clamping correct, and under what condition is it actively harmful?
- With the near channel active and clamping **on**, describe the failure. Why does it present as "particles flying apart" rather than as anything obviously clamp-shaped?
- The CPU expresses this as a `bool` in `SolverParams`, which needs `[MarshalAs(UnmanagedType.U1)]` to be blittable. On the GPU it crosses as a `uint` compared against `0`. Why can HLSL not simply take a `bool` uniform here, and what is the equivalent C# problem?
- How would you detect, from output alone, that the clamp flag had been silently dropped during the port? (Consider: what would you see with `clampPositive = false` that you would not see with it honoured?)
- The verification for this task checks *both* branches. Why is testing only the default branch insufficient evidence that the flag was ported?

## Snippet 6 — Scalars in their own buffers

```hlsl
RWStructuredBuffer<float> _Density;
RWStructuredBuffer<float> _NearDensity;
RWStructuredBuffer<float> _Pressure;
RWStructuredBuffer<float> _NearPressure;
```

```csharp
density = new ComputeBuffer(particleCapacity, sizeof(float), ComputeBufferType.Structured);
nearDensity = new ComputeBuffer(particleCapacity, sizeof(float), ComputeBufferType.Structured);
```

**Explain:**
- The `Particle` struct already has `density`, `pressure`, `nearDensity` and `nearPressure` fields. Why not write into those and save four buffers?
- In the density pass, thread `i` writes only element `i` but reads **every** element's position. If density were stored in the `Particle` struct, what race would exist? Is it harmful — and why is "it is not harmful" the wrong reason to accept it?
- This is the same decision the CPU made in T-024 (SoA) and T-025 (no pass writes a field another reads). What does that repetition say about the two implementations?
- If forces at T-028 need density and pressure, where do they read them from? Does keeping them in separate buffers make T-028 harder or easier?
- Four `float` buffers at capacity 400 is 6.4 KB. Why is memory not the reason to care about this decision?

- `_ParticleCount` is copied into a uniform even though the dispatch group count already implies it. Why does the shader still need it?

## Snippet 8 — Establishing "matches the CPU"

```
[CMP] clamp=False density       maxAbs=3.662E-004 maxRel=2.568E-007 ok=True
[CMP] clamp=False pressure      maxAbs=7.500E-001 maxRel=5.699E-005 ok=True
[CMP] clamp=True  pressure      cpu[0]=0.0000 gpu[0]=0.0000 ok=True
[CMP] clamp=True  produced no negative GPU pressures (expected)
```

**Explain:**
- The comparison runs the real `ComputeDensityJob`/`ComputePressureJob` on the CPU and the real kernels on the GPU over the same positions. Why is running the *actual* CPU code the important part, rather than re-deriving the expected density in the test?
- Density matches to `3.7e-4` absolute (~`2.6e-7` relative), but pressure matches only to `5.7e-5` relative. Both are within tolerance. Why is pressure's relative error larger when it is a pure function of density?
- The tolerance is relative, with a floor of `1e-6` on the denominator. Why does a pure relative test fail on a field that is legitimately zero, and what does the floor do about it?
- `clamp=True` produces pressure exactly `0.0` where the raw value was negative. What would the check `negatives != 0 → fail` catch that a value comparison alone might not?
- Both runs spawn particles randomly, so the two runs do not use identical layouts. Why does that not weaken the comparison?
- This was verified headlessly via Metal in batch mode. What can it **not** tell you about the GPU path?
