# T-031 Understanding — GPU Count Sort & Prefix Scan

Explain each snippet in your own words. Focus on **why** each choice was made and what breaks without it.

> **This task does more than its Guide asks.** The Guide and Done criterion only require *building* the structure ("kernels **can** query `_CellStart`"). That alone would have changed no timings — T-030 already produced keys and bought nothing. The task therefore also rewires the three O(N²) kernels to consume the grid, which is where the 27.8× at N=10k comes from. Sections 4–6 cover that half.

## Snippet 1 — Packed indexing: boundary particles share the structure

```
[0, _ParticleCount)              fluid particles, in _ParticlesIn
[_ParticleCount, _TotalCount)    boundary particles, in _BoundaryPositions
```

```hlsl
float2 PositionOfPacked(uint p)
{
    if (p < _ParticleCount) return _ParticlesIn[p].position;
    return _BoundaryPositions[p - _ParticleCount];
}
```

**Explain:**
- This mirrors the CPU grid's packing exactly (T-023). Why is reusing the same scheme worth more than inventing a GPU-specific one?
- The force kernel's wall loop was O(N·B) before this. Show that `B ∝ √N` for a fixed container, and state the resulting complexity. Why is O(N^1.5) invisible today but fatal later?
- At N=10k the boundary loop was only ~3% of the old O(N²) cost. So why fix it now rather than when it becomes a problem?
- Boundary particles never move, so their cell membership is fixed forever. What would it cost to exploit that, and why is it not worth it at these sizes?
- `PositionOfPacked` is called inside the force kernel's inner loop. Why does the branch not hurt, and what would make it hurt?

## Snippet 2 — The three passes

```hlsl
void ClearBuckets(...)      { if (b < _BucketCount) _BucketStart[b] = 0u; }

void CountBuckets(...)      { InterlockedAdd(_BucketStart[_CellKeys[p]], 1u); }

void PrefixSumBuckets(...)  { /* exclusive scan, in place */ }

void ScatterParticles(...)
{
    uint slot;
    InterlockedAdd(_BucketCursor[_CellKeys[p]], 1u, slot);
    _SortedIndices[slot] = p;
}
```

**Explain:**
- Why is `_BucketStart` used as the histogram, then overwritten with the offsets? What does the array mean on entry to `PrefixSumBuckets` versus on exit?
- `_BucketStart` has `_BucketCount + 1` entries. Which query line needs the extra slot, and why does it remove a special case?
- The scatter needs a *consumable* cursor, so it cannot use `_BucketStart`. Why not? What invariant does the query rely on that a consuming cursor would destroy?
- Within a bucket the scatter order is arbitrary, because atomics decide it. Which kernels does that affect, and how much does it change their results?
- Why does `ClearBuckets` need a bounds check (`if (b < _BucketCount)`) when `CountBuckets` does not need one for `p`? (Compare how each is dispatched.)
- The two-argument `InterlockedAdd` returns `void`; returning the old value needs a third `out` parameter. What does that tell you about how HLSL atomics are specified compared to C#'s `Interlocked`?

## Snippet 3 — The prefix sum

```hlsl
groupshared uint _scanTile[SCAN_THREADS];

for (uint base = 0u; base < _BucketCount; base += SCAN_THREADS)
{
    uint v = (i < _BucketCount) ? _BucketStart[i] : 0u;
    _scanTile[t] = v;
    GroupMemoryBarrierWithGroupSync();

    for (uint offset = 1u; offset < SCAN_THREADS; offset <<= 1)
    {
        uint other = (t >= offset) ? _scanTile[t - offset] : 0u;
        GroupMemoryBarrierWithGroupSync();
        _scanTile[t] += other;
        GroupMemoryBarrierWithGroupSync();
    }

    uint exclusive = carry + _scanTile[t] - v;
    carry += _scanTile[SCAN_THREADS - 1];
}
```

**Explain:**
- This is a Hillis-Steele scan, not the Blelloch scan the Guide names. What is the difference in work and in span, and which one is easier to get right?
- Why does the outer loop process tiles **in order**, carrying a total? What breaks if tiles were processed in any order?
- There are two barriers inside the inner loop. What is the first one for, and what would happen without it?
- `exclusive = carry + _scanTile[t] - v` reconstructs the exclusive prefix from the inclusive one. Why not compute the exclusive form directly?
- Why is the whole scan done by one workgroup rather than many? Give the number that makes this acceptable, and say when it would stop being acceptable.
- The scan is in place: thread `t` reads `_BucketStart[base+t]` and later writes the same slot. Why is that safe here, given that other threads are reading their own slots?
- `if (t == 0u) _BucketStart[_BucketCount] = carry;` — all threads compute the same `carry`. Why is it still written by one thread only?

## Snippet 4 — The query: skip, never clamp

```hlsl
uint key = KeyForCell(int2(cx, cy));
uint start = _BucketStart[key];
uint end = _BucketStart[key + 1];

for (uint s = start; s < end; s++)
{
    uint q = _SortedIndices[s];
    ...
}
```

```csharp
// Out-of-grid cells are SKIPPED, never clamped. Clamping would make KeyForCell
// return the edge cell for several deltas, so an edge particle would scan the
// same bucket up to four times and double-count its occupants.
if (cx < 0 || cx >= (int)_GridCols) continue;
```

**Explain:**
- `KeyForCell` *clamps* in direct mode, yet the query must not rely on that. Reconcile the two.
- Construct the double-counting failure concretely: a particle in cell `(0, 3)`, and the nine `(dx, dy)` deltas. Which deltas clamp to the same bucket, and how many times is that bucket scanned?
- What is the *symptom* of double-counting in density? Would it look like a bug, or like slightly wrong fluid?
- The distance test would still reject non-neighbours, since the kernel returns zero beyond `h`. So is the skip an optimisation or a correctness requirement? Justify carefully.
- With cell size exactly `h`, the 3×3 block is guaranteed to contain every neighbour. Prove the boundary case: a particle at the very left edge of its cell, and a neighbour exactly `h` away — which cell is that neighbour in?
- The query still keeps an explicit `r2 >= h2` test even though the grid guarantees `r < 3h`. Why can that test not be dropped? (See T-028's note about the gradient functions.)
- `ComputeDensity` and `ComputeViscosity` treat boundary particles differently. State the rule for each and why they differ.

## Snippet 5 — Verification: validating a structure, not a number

```
[T031] grid n=400 total=748 buckets=441 startMismatch=0 duplicates=0
       outOfRange=0 missing=0 misplaced=0 problems=0
[T031] 10-step cpu-vs-gpu (gridded) maxPosErr=9.537E-007 maxVelErr=5.395E-006 ok=True
```

**Explain:**
- A prefix sum is either exactly right or meaningless — there is no useful tolerance. What is the strongest check you can write for it, and why is "the simulation looks fine" not one?
- `startMismatch` histograms the GPU's own keys on the CPU and rebuilds the offsets. Why compute the reference from the GPU's keys rather than from CPU-derived keys?
- `duplicates` + `missing` together establish that `_SortedIndices` is a permutation. Why does that matter even though a duplicate would not crash anything?
- `misplaced` walks both arrays and checks that each slot's occupant belongs to the bucket that owns that slot. What class of bug does that catch that the histogram comparison does not?
- The second check runs 10 full steps on both CPU and GPU from the same seed. Why is it still needed, given the structure is already proven valid?
- The benchmark derives `h` per N, while T-029's did not. Explain why brute force is `h`-independent but the grid is not, and why that makes the comparison fair anyway.
- At n=400 the speedup is only 2.4× but at n=10k it is 27.8×. Explain both, in terms of fixed overhead and of what the grid actually removes.

## Snippet 6 — What changed in complexity

```
brute force → gridded
  n=400     1.29 → 0.54 ms
  n=10000  29.25 → 1.05 ms
  n=50000     —  → 3.65 ms
```

**Explain:**
- Give the complexity of the old density kernel and the new one, in terms of N, the average neighbours `k`, and the 9-cell candidate count `c`.
- `c ≈ 43` at N=10k. How many of those are true neighbours? Why is the gap not a bug?
- The 3×3 scan is performed separately in density, force, and viscosity — three times per step. What optimisation does that suggest, and what would it cost in memory?
- The grid rebuild is now a real cost that grows with N. Which passes of the five are O(N) and which are O(buckets)? Which one would you attack first if the rebuild became the bottleneck?
- At n=50000 the step is 3.65 ms, i.e. ~274 fps. What is the *next* thing you would expect to become the bottleneck, and which task addresses it?
- T-030's default key mode is DirectIndex. Would the hash mode have changed any of these numbers? Refer to the T-030 measurement.
