## Snippet 1 — The struct is a contract, not a convenience

```hlsl
struct Particle
{
    float2 position;     // offset  0
    float2 velocity;     // offset  8
    float2 force;        // offset 16
    float density;       // offset 24
    float pressure;      // offset 28
    float nearDensity;   // offset 32
    float nearPressure;  // offset 36
};                       // 40 bytes
```

```csharp
public struct Particle2D
{
    public float2 position;
    public float2 velocity;
    public float2 force;
    public float density;
    public float pressure;
    public float nearDensity;
    public float nearPressure;
}
```

```csharp
public const int ParticleStride = sizeof(float) * 10;
```

**Explain:**
- Nothing checks that these two structs agree. What is the actual failure mode if a field is added to one and not the other — a crash, garbage values, or something quieter?
- Every `float2` sits at an 8-byte offset and every `float` at a 4-byte one, giving 40 bytes with no padding. If you reordered the fields so `density` came first, would the size change? Would the offsets?
- Why does the stride get computed with `sizeof(float) * 10` rather than hardcoded `40`?
- The renderer already uploads this same struct at the same stride. What work does that save at T-032, and what would have been lost if `SPHCompute` had invented its own GPU layout instead?
- `ParticleState` on the CPU is a structure of *arrays*; the GPU buffer is an array of *structs*. Why is that not a contradiction?

## Snippet 2 — Two particle buffers, not one

```hlsl
StructuredBuffer<Particle> _ParticlesIn;
RWStructuredBuffer<Particle> _ParticlesOut;
```

```csharp
particlesIn  = new ComputeBuffer(particleCapacity, ParticleStride, ComputeBufferType.Structured);
particlesOut = new ComputeBuffer(particleCapacity, ParticleStride, ComputeBufferType.Structured);
```

**Explain:**
- Why is the input buffer declared `StructuredBuffer` and the output `RWStructuredBuffer`, rather than both being read-write?
- A single read-write buffer would also work for this kernel, since thread `i` only touches element `i`. What does the split buy in terms of *debugging* — what can you inspect that you could not with one buffer?
- What does this split cost in memory, and why is that cost trivially small next to the particle data itself?
- At T-028 integration writes positions. Does an in-place read-modify-write on one buffer become safe there? What is the condition?

## Snippet 3 — Boundary particles as one buffer and one scalar

```hlsl
// Boundary particles are static: uploaded once, never written, never integrated.
StructuredBuffer<float2> _BoundaryPositions;
float _BoundaryVolume;
```

```csharp
// Park a one-element boundary buffer immediately. The kernel reads element
// zero unconditionally, so it must never be null, and a zero-length
// ComputeBuffer cannot be allocated at all.
boundary = new ComputeBuffer(1, sizeof(float) * 2, ComputeBufferType.Structured);
boundary.SetData(new[] { new float2(1e9f, 1e9f) });
```

**Explain:**
- The CPU side already parks a one-element boundary array. Why does the same trick have to be repeated on the GPU rather than inherited?
- Why is a zero-length `ComputeBuffer` impossible to allocate, and what does the kernel's unconditional `_BoundaryPositions[0]` read have to do with it?
- State the GPU Port Decision #2 recorded in `docs/TASKS.md`, and the consequence it avoids. Which earlier task's bug returns if you instead "drop them and rely on the clamp"?
- Boundary particles never move. Name two costs that this fact removes on the GPU — one about buffers and one about synchronisation.
- Why does the boundary buffer hold `float2` while the particle buffer holds a 40-byte struct?

## Snippet 4 — Dispatch geometry and the bounds check

```hlsl
[numthreads(64, 1, 1)]
void ProbeRoundTrip(uint3 id : SV_DispatchThreadID)
{
    uint i = id.x;

    // Dispatch always rounds up to a whole number of thread groups, so the final
    // group can contain threads past the end of the array.
    if (i >= _ParticleCount) return;
    // ...
}
```

```csharp
int groups = (particleCapacity + ThreadGroupSize - 1) / ThreadGroupSize;
shader.Dispatch(kernel, groups, 1, 1);
```

**Explain:**
- Why does the C# side round *up* rather than use `particleCapacity / ThreadGroupSize`? Work through `particleCount = 400` and `particleCount = 401`.
- Given the rounding, how many threads can be past the end of the array at most? Why is that bounded rather than arbitrary?
- What goes wrong if the bounds check is removed for a full group but kept "because it usually divides evenly"? What *specifically* is corrupted — and note that an out-of-bounds write on a `RWStructuredBuffer` does not necessarily crash.
- The `[numthreads(64,1,1)]` value and `ThreadGroupSize = 64` in C# must agree. What is the symptom if they silently diverge? Does the bounds check save you?
- Why is the group count on the x axis only, and what would 2D `numthreads` imply about the particle indexing?

## Snippet 5 — What the self test actually proves

```csharp
p.position += _ProbeOffset;   // proves the particle round trip
p.force     = _BoundaryPositions[0];   // proves the boundary buffer is bound
p.density   = _BoundaryVolume;         // proves the scalar constant path
```

```csharp
float2 expectedPosition = input[i].position + ProbeOffset;
bool positionOk = math.all(math.abs(output[i].position - expectedPosition) <= 1e-5f);
bool boundaryOk = math.all(output[i].force == wallPosition);
bool volumeOk   = math.abs(output[i].density - boundaryVolume) <= 1e-6f;
```

**Explain:**
- Why are there three checks rather than one? What class of failure does each catch that the others cannot?
- A stale or zeroed buffer would return all zeros. Would the boundary-value check pass or fail on an all-zero buffer if `wallPosition` were `(0,0)`? Why was it chosen as `(7.5, -3.25)` instead?
- The position check uses a tolerance of `1e-5` while the boundary and volume checks use exact/`1e-6` comparison. Why does the first need a tolerance and the others not?
- The kernel *overwrites* `force` and `density` rather than adding to them. Why is that the right choice for a probe, and what would adding hide?
- This test dispatches, reads back on the same call, and does not render. What can it therefore NOT tell you about the pipeline?

## Snippet 6 — Buffer lifetime and the managed hop

```csharp
public void Release()
{
    particlesIn?.Release();
    particlesOut?.Release();
    boundary?.Release();
    particlesIn = null;
    particlesOut = null;
    boundary = null;
    readbackScratch = null;
    // ...
}
```

```csharp
// ComputeBuffer in this Unity version exposes GetData only for managed arrays,
// not for NativeArray, so the copy goes buffer -> managed scratch -> NativeArray.
if (readbackScratch == null || readbackScratch.Length != particleCapacity)
{
    readbackScratch = new Particle2D[particleCapacity];
}

particlesOut.GetData(readbackScratch, 0, 0, particleCapacity);
NativeArray<Particle2D>.Copy(readbackScratch, into, particleCapacity);
```

**Explain:**
- `ComputeBuffer` is unmanaged, like `NativeArray`. What happens if `Release()` is never called, and why does re-entering play mode make that visible?
- Why is `OnDestroy` the right place for the release, and what would leak if the component were instead re-initialised every frame?
- `SetData` accepts a `NativeArray<Particle2D>`, but `GetData` does not. Where does that asymmetry show up in the code, and what does it cost?
- Why is `readbackScratch` cached on the component instead of allocated per call? What would per-call allocation do to a frame that runs this 60 times a second?
- The step is described as temporary because T-029 removes the readback. Why keep it at all in T-026 rather than going straight to the GPU-resident design?

## Snippet 7 — What T-026 deliberately does not do

```csharp
/// T-026 is plumbing only: allocate, upload, dispatch one kernel, read back.
/// Physics is deliberately absent — T-027 adds density and pressure, T-028 adds
/// forces and integration, T-029 removes the per-frame readback.
```

**Explain:**
- Why is the data flow separated from the physics, rather than writing one kernel that already computes density?
- T-027 will need a neighbour structure on the GPU. Which Phase 2 artifact is *not* being ported here, and what does T-030/T-031 exist to replace?
- The `SolverParams` C# struct is described as becoming the compute shader's constant buffer "almost verbatim". What has to change about it before HLSL can take it directly? (Look at its field types.)
- At T-029 the buffers stay resident and only dispatch remains. Which method in `SPHCompute` becomes the hot path, and which one disappears?
- Nothing in this task is wired into `SPH2D` yet. Why is that correct scope, and what would break if `SPHCompute` and `SPH2D` both owned particle state now?
