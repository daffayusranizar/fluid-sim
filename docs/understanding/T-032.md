# T-032 Understanding — GPU Instanced Particle Rendering

Explain each snippet in your own words. Focus on **why** each choice was made and what breaks without it.

> The instanced shader and the `DrawMeshInstancedIndirect` call already existed. This task's real subject is the **source of the buffer**: the renderer stops uploading CPU state and binds the solver's own GPU buffer. Section 1 is that change; section 5 is about verifying something whose output is pixels.

---

## Snippet 1 — Binding versus uploading

```csharp
// Before: pack and upload every frame
NativeArray<Particle2D> particles = sim.Particles;
EnsureBufferCapacity(particles.Length);
particleBuffer.SetData(particles);
```

```csharp
// After: bind the solver's own buffer
if (gpuSource != null && gpuSource.IsReady)
{
    Render(gpuSource.ParticleBuffer, gpuSource.ParticleCapacity);
    return;
}
```

**Explain:**
- `SetData` on 400 particles is 16 KB per frame. At 50,000 it is 2 MB per frame. Why is that bandwidth cost not the main problem?
- The real cost of `SetData` is that it forces the simulation state to exist on the CPU. Trace that back: what has to happen before `sim.Particles` contains anything, and what does that imply for T-029's "zero readback" claim?
- The GPU path and the CPU path bind the *same struct layout* to the same shader. What does that tell you about how the two paths can coexist?
- `gpuSource.IsReady` is the gate. What is it false for, and why does that make the renderer's fallback automatic rather than something a user has to configure?
- `SPHCompute.ParticleBuffer` is a property returning `ParticlesIn`. Why does it return `null` when not ready rather than exposing the field directly?

## Snippet 2 — The args buffer owns the instance count

```csharp
private static ComputeBuffer CreateArgsBuffer(Mesh mesh, int instanceCount)
{
    var args = new uint[5];
    args[0] = mesh.GetIndexCount(subMesh);
    args[1] = (uint)instanceCount;
    ...
}
```

```csharp
if (boundBuffer != buffer || boundCount != count)
{
    material.SetBuffer("Particles", buffer);
    ReleaseBuffer(ref argsBuffer);
    argsBuffer = CreateArgsBuffer(quad, count);
    boundBuffer = buffer;
    boundCount = count;
}
```

**Explain:**
- Why is the instance count inside a GPU buffer rather than a C# argument to the draw call? What does "indirect" mean here?
- With `DrawMeshInstancedIndirect`, the CPU cannot see the instance count. What is the practical consequence — how does the renderer know how many particles to draw?
- The rebind is guarded by comparing both the buffer *and* the count. Name a case where the buffer is unchanged but the count is not.
- Why compare at all, rather than calling `SetBuffer` and rebuilding the args buffer every frame? What is the cost of `material.SetBuffer` on a steady frame?
- `boundCount` is guessed from `gpuSource.ParticleCapacity`. Is that necessarily the number of *live* particles? What would break if the solver's capacity and its active count diverged?
- Why does the renderer keep its own quad mesh instead of using a primitive?

## Snippet 4 — The shader, unchanged but now load-bearing

```hlsl
Varyings vert(Attributes IN, uint instanceID : SV_InstanceID)
{
    Particle p = Particles[instanceID];
    float speed = length(p.velocity);
    float t = saturate(speed / max(_VelocityMax, 1e-5));
    OUT.colour = ColourMap.SampleLevel(sampler_ColourMap, float2(t, 0.5f), 0).rgb;

    float3 worldPos = float3(p.position + IN.vertex.xy * _ParticleRadius, 0);
    OUT.positionCS = TransformWorldToHClip(worldPos);
    ...
}
```

```hlsl
float delta = fwidth(sqrt(sqrDst));
float alpha = 1.0f - smoothstep(1.0f - delta, 1.0f + delta, sqrDst);
```

**Explain:**
- The quad is built in **world space** and the object transform is skipped. What does that buy, and what does it cost when the GameObject is moved?
- `SV_InstanceID` indexes the buffer directly. What would change if the renderer had to sort or filter particles before drawing?
- `fwidth` makes the antialiasing band one pixel wide regardless of zoom. What would a fixed-width band look like when zoomed in, and when zoomed out?
- `t = saturate(speed / max(_VelocityMax, 1e-5))`. Why is the `max` there? What happens at speed 0?
- This bit the verification: with all particles at rest, `t = 0`, which samples the **first** colour of the gradient. Why does that matter when choosing a gradient, and what did the test have to change?
- The particle plane is at world `z = 0` and the camera sits at `z = -10`. What must be true about the camera's far clip, and which earlier scene bug was exactly this?

## Snippet 5 — Verifying pixels

```csharp
RenderPipelineManager.beginCameraRendering += OnBeginCamera;
cam.Render();
RenderPipelineManager.beginCameraRendering -= OnBeginCamera;
```

```
[T032] render n=400 litPixels=6411 coverage=9.78% spreadX=0.26 spreadY=0.68 ownBuffer= ok=True
[T032] cpu cost n=50000 msPerFrame=0.291 impliedFps=3442
```

**Explain:**
- In play mode `LateUpdate` runs before the render pipeline, so a `Graphics.DrawMeshInstancedIndirect` issued there is picked up. Why does an editor script need the callback instead?
- `spreadX` and `spreadY` measure the bounding box of lit pixels. A single blob at the origin would light many pixels too. Why is spread the right discriminator between "particles rendered" and "one particle rendered 400 times at the same place"?
- The first attempt reported `litPixels=0` while the diagnostics showed a valid material, a bound buffer, and `args=[6,400,0,0,0]`. Describe how you would narrow that down, and what the `RenderProbe2` isolation actually established.
- `maxLum` was 66 — not zero. What does that tell you, and why is "zero lit pixels" a misleading way to describe it?
- The second trap was `x=[-10,-4]`: the harness's `AddComponent<SPH2D>()` used the C# default `boxSize = 20×20`, not the scene's 10×10. What general lesson does that teach about testing a component outside its scene?
- The 50k timing includes a full camera render and a `/1000` fps that is not a real frame rate. What is the number actually measuring, and why is it still useful?
- What can this test **not** establish about "smooth filled circles" that only looking at the screen can?

## Snippet 6 — Wiring the scene

```yaml
shader: {fileID: 7200000, guid: fd5605c00537460a8d4612d44371e30a, type: 3}
```

**Explain:**
- A `ComputeShader` asset uses `fileID: 7200000`; a `Shader` asset uses `4800000`. What happened when the wrong one was written, and why was that failure silent rather than an error?
- The scene check reported `compute.shader=NULL` while `gpuSim.source`, `gpuSim.compute` and `renderer.gpuSource` all resolved. What does comparing those four results tell you about where to look?
- The reference was fixed by having Unity serialise it and reading back the YAML. Why is that more reliable than looking the id up in documentation?
- `SPH2D.solveOnCpu` must be false for the GPU run, and `showParticleGizmos` was turned off. What would the Scene view show if only the first were done?
- All three references (`gpuSource`, `source`, `compute`) are resolvable by `GetComponent`. Why keep them as serialised fields at all rather than removing them and always using `GetComponent`?
