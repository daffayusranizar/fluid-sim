## Snippet 1 — The quad is a disc, but the fragment makes it a sphere

```hlsl
void ImpostorFront(float2 local, float2 centre, out float3 worldFront, out float h)
{
    float sqrDst = dot(local, local);
    h = sqrt(max(0.0, 1.0 - sqrDst));

    // The quad spans -0.5..0.5 before scaling, so the disc's world radius is
    // half of _ParticleRadius.
    float discRadius = 0.5 * _ParticleRadius;
    worldFront = float3(centre + local * discRadius, -h * discRadius);
}
```

**Explain:**
- Confusingly, the world-space disc radius is **half** `_ParticleRadius`. Why? What does the quad's vertex data span before scaling?
- `h` is reconstructed per fragment, not interpolated from the vertices. Why can the four corner vertices not carry it?
- What is `h` at the centre of the disc, and at the rim? What does the profile look like in cross-section?
- The world `z` offset is `-h * discRadius`, i.e. negative. The camera sits at `z = -10` looking toward `+z`. Why negative, and what would happen visually if the sign flipped?
- Before this change the quad was built at `float3(p.position + IN.vertex.xy * _ParticleRadius, 0)` — `z` hardcoded to `0`. Name the two separate features that a constant `z` blocks.

```hlsl

float3 n = normalize(cross(ddy(P), ddx(P)));
```

**Explain:**

- The normal is `cross(ddy(P), ddx(P))` — the arguments are swapped relative to the usual order. What does the swap change, and how did the sign of `n.z` decide it?
- The camera is assumed orthographic and axis-aligned, so `uv` maps linearly onto the view plane and no projection matrix is inverted. What would this reconstruction have to do instead for a perspective camera?

## Snippet 6 — The depth prepass, and why it cannot be the colour pass

```hlsl
Blend One One
BlendOp Min
ZWrite Off
ZTest Always
ColorMask R

float frag(Varyings IN) : SV_Target
{
    float sqrDst = dot(IN.local, IN.local);
    if (sqrDst > 1.0) return _FarDepth;

    float3 worldFront;
    float h;
    ImpostorFront(IN.local, IN.centre, worldFront, h);

    return -TransformWorldToView(worldFront).z;
}
```

**Explain:**
- The surface needs the **front-most** depth per pixel. Why is that a min-reduction rather than an average, and why can the alpha-blended colour pass not produce it?
- Why is the background cleared to `_FarDepth` instead of 0, and what does that make "there is no fluid here" mean?
- Out-of-disc fragments return `_FarDepth` rather than being discarded. Why is returning the far value the same decision as clearing to it?
- `-TransformWorldToView(worldFront).z` gives a camera-relative depth. Why is that better than writing world `z`, or a hand-computed distance?
- Depth is written to an **RFloat** target rather than RHalf. Half precision at a camera distance of ~10 quantises in steps of ~0.01. How large is a particle radius, and what would that quantisation do to the reconstructed normals?
- `ZTest Always` with `ZWrite Off`: why does the min blend make the depth buffer unnecessary here?
- The offscreen pass runs from a `CommandBuffer`, which has **no camera context**. What breaks if the view and projection matrices are not set explicitly?

## Snippet 7 — The bilateral blur, and the trap in its ordering

```hlsl
if (centre >= _FarDepth * 0.5) return _FarDepth;

for (int i = -Radius; i <= Radius; i++)
{
    float d = SampleDepth(IN.uv + step * i);
    if (d >= _FarDepth * 0.5) continue;

    float spatial = exp(-(float)(i * i) / (2.0 * 12.0));
    float diff = d - centre;
    float range = exp(-(diff * diff) / (2.0 * _RangeSigma * _RangeSigma));

    sum += d * (spatial * range);
    weightSum += spatial * range;
}
```

**Explain:**
- A plain Gaussian blur over depth would smooth the interior *and* melt the silhouette into the background. Which term prevents the second, and how?
- Why does the fragment need *both* early returns (centre is background, neighbour is background) rather than just one?
- `_RangeSigma` has to be comparable to the scallop depth between adjacent particles. What happens if it is far too small, and what if it is far too large?
- The blur is separable into two axis passes. Why is that valid for the *spatial* term, and why is it only an approximation once the range term depends on the data?
- **The trap:** `Graphics.Blit(src, dst, material)` defaults to pass `-1`, which runs more than one pass; and `Graphics.DrawMesh(mesh, m, material, layer)` draws pass 0 with no way to name another. Given both, why must the composite be pass 0 and the blur be pass 1, and why must every blit name its pass explicitly?
- **The other trap:** `DrawMeshInstancedIndirect(mesh, submeshIndex, material, shaderPass, args)`. What did passing `(quad, 1, material, 0, args)` actually ask for, and what error did it produce?
- The failure above is still unexplained: a background pixel reading 512 in the source reads 0 after the pass. If the filter logic cannot produce that, where do you look next, and what is the smallest experiment that separates "the target is not being written" from "the source is not being sampled"?
