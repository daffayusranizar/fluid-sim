## Snippet 1 — Structure of arrays is the precondition, not the optimisation

```csharp
public struct ParticleState
{
    public NativeArray<float2> position;
    public NativeArray<float2> velocity;
    public NativeArray<float2> force;

    public NativeArray<float> density;
    public NativeArray<float> pressure;

    public NativeArray<float> nearDensity;
    public NativeArray<float> nearPressure;
}
```

> *"1. No data race. Each pass writes exactly one array and reads others. With an array of structs, writing `particles[i]` rewrites position and velocity too, while other threads are reading `particles[j].position` as a neighbour. That race is benign in practice — the rewritten values are unchanged — but it is still a race, and correctness should not rest on a coincidence."*

**Explain:**
- Which of the three stated reasons is about **correctness** and which are about **speed**? Be specific.
- With an array of structs, thread A writes `particles[i]` while thread B reads `particles[j].position`. The bytes B reads were never actually changed by A. Why is this still a data race, and why is "the values are unchanged" not a defence?
- Reason 2 says Burst cannot vectorise when one array is both read and written. What does Burst have to assume about the two pointers, and how does splitting `position` and `force` remove that assumption?
- This refactor happened in T-024 (for Burst), and only now pays off for threads. Why couldn't T-025 have been done first, on top of the old `Particle2D[]`?

## Snippet 2 — One pass per job, one written array each

```csharp
[BurstCompile]
public struct ResetForcesJob : IJobParallelFor
{
    [WriteOnly] public NativeArray<float2> force;

    public void Execute(int i)

```

**Explain:**
- `IJobParallelFor` calls `Execute(i)` once per index. What is Unity's guarantee about which indices a single invocation may touch, and which lives inside that guarantee?
- State the safety invariant in one sentence, the way the file header does. Every job here satisfies it — how?
- `[ReadOnly]` / `[WriteOnly]` are not just documentation. Which system consumes them, and what does it do when you get them wrong? What does Burst do with the same information?
- `Execute(int i)` is a *method*, not a field. How does the job struct — a plain blittable struct with no methods called on it before `Schedule` — end up running code on worker threads?
- Why can density and pressure be separate jobs at all, while density and pressure *force* cannot?

## Snippet 3 — The dependency graph

```csharp
JobHandle density = new ComputeDensityJob { ... }.Schedule(count, batch);

JobHandle pressure = new ComputePressureJob { ... }.Schedule(count, batch, density);

JobHandle reset = new ResetForcesJob { ... }.Schedule(count, batch);

JobHandle pressureForce = new ComputePressureForceJob { ... }
    .Schedule(count, batch, JobHandle.CombineDependencies(reset, pressure));

JobHandle viscosity = new ComputeViscosityJob { ... }.Schedule(count, batch, pressureForce);

viscosity.Complete();
```

```
///   ResetForces -> ComputePressureForce -> ComputeViscosity   (all touch force)
///   ComputeDensity -> ComputePressure                         (pressure needs density)
///   ComputePressureForce -> Integrate                         (integration needs force)
```

**Explain:**
- `pressureForce` depends on **both** `reset` and `pressure`. Name the two distinct reasons — one is about a value being ready, one is about two writers colliding on the same array.
- Trace what goes wrong if you drop the `reset` dependency and let `ResetForcesJob` and `ComputePressureForceJob` run concurrently. The result is not a crash — describe the wrong output.
- `JobHandle.CombineDependencies` exists because `Schedule(count, batch, handle)` takes exactly one handle. Why is a *single* handle insufficient here, and what does the combine produce?
- The header says the force jobs are split "rather than fused … at the cost of one dependency." Fusing `ComputeViscosityJob` into `ComputePressureForceJob` would be safe (both only touch index `i`), so what is actually being bought by keeping them apart?
- `viscosity.Complete()` is the only completion inside `SolveStep`. Why must it be **inside** the step, before the next `RebuildNeighbors()`, rather than deferred to `LateUpdate`?

## Snippet 4 — Read-modify-write is where parallelism stops

```csharp
[BurstCompile]
public struct ComputeViscosityJob : IJobParallelFor
{
    [ReadOnly] public NativeArray<float2> position;
    [ReadOnly] public NativeArray<float2> velocity;
    [ReadOnly] public NeighborLists neighbors;

    [WriteOnly] public NativeArray<float2> viscosityForce;

    // Read and written: this pass accumulates on top of the pressure force, which
    // is why it must be scheduled as a dependent job rather than in parallel.
    public NativeArray<float2> force;

    public void Execute(int i)
    {
        // ...
        force[i] += viscForce * p.viscosity;
    }
}
```

**Explain:**
- `force` carries neither attribute. What is the job telling the safety system by declaring it plain, and why is it still race-free *within* this one job?
- `ResetForcesJob` writes `force` with `[WriteOnly]`. Both jobs write the same field of the same struct type. Why is one `[WriteOnly]` and the other not?
- `ComputePressureForceJob` assigns `force[i]` from scratch; this pass reads it and adds. Both are index-disjoint. Why is index-disjointness sufficient *inside* one job, yet not sufficient *between* two separate jobs that write the same array?
- `viscosityForce` exists only for the debug arrows, and costs an extra array and an extra write per particle. Why does that cost essentially nothing in the parallel version, whereas it would have shown up in the serial timings?
- `[NativeDisableParallelForRestriction]` is named in the task guide but appears nowhere in this file. Why is that correct? When would you actually need it?

## Snippet 5 — CSR neighbour lists are what make neighbour loops parallel-safe

```csharp
/// Particle i's fluid neighbours are fluid[fluidStart[i] .. fluidStart[i + 1]],
/// and its boundary neighbours are boundary[boundaryStart[i] .. boundaryStart[i + 1]].
///
/// This replaces List<int>[] because Burst cannot touch managed types. The layout
/// also happens to be exactly what a parallel job wants at T-025: each particle
/// reads only its own contiguous range of a read-only array, so no writes to
/// shared state and no race conditions.
public struct NeighborLists
{
    public NativeArray<int> fluidStart;
    public NativeArray<int> fluid;
    public NativeArray<int> boundaryStart;
    public NativeArray<int> boundary;
}
```

```csharp
int start = neighbors.fluidStart[i];
int end = neighbors.fluidStart[i + 1];

for (int k = start; k < end; k++)
{
    int n = neighbors.fluid[k];
    // ...
}
```

**Explain:**
- The old layout was `List<int>[]`. Give the two independent reasons it cannot survive T-025.
- Every thread reads `neighbors.fluidStart[i]` and `neighbors.fluidStart[i + 1]` for its *own* `i`, and `fluidStart` is never written during the solve. Why does that make the shared array safe to read concurrently?
- The array has `fluidCount + 1` entries. Which single particle's range would be broken without the extra slot, and why is that an off-by-one that never crashes?
- `SPHGrid.Rebuild()` returns a `NeighborLists` **by value**, holding copies of the `NativeArray` handles. Why must the caller re-read the returned struct after every rebuild instead of caching it?
- T-023 built this structure and T-025 consumed it unchanged. What does that say about where the phase boundary between T-023 and T-025 actually sits?

## Snippet 7 — A job field must be a constructed container before `Schedule`

```csharp
/// Keeps a one-element boundary array around when there are no boundary
/// particles, so jobs are never handed an uncreated NativeArray.
private void ParkDisabledBoundaryArray()
{
    boundaryCount = 0;

    if (boundaryParticles.IsCreated) boundaryParticles.Dispose();

    boundaryParticles = new NativeArray<float2>(1, Allocator.Persistent);
    boundaryParticles[0] = new float2(1e9f, 1e9f);
}

/// The boundary array as the solver should see it. Self-healing rather than
/// relying on Awake ordering: getting this wrong throws at schedule time with a
/// message that says nothing about boundary particles.
private NativeArray<float2> BoundaryView()
{
    if (!boundaryParticles.IsCreated) ParkDisabledBoundaryArray();
    return boundaryParticles;
}
```

```
InvalidOperationException: The UNKNOWN_OBJECT_TYPE ComputeDensityJob.boundaryPositions
has not been assigned or constructed. All containers must be valid when scheduling a job.
```

**Explain:**
- The exception names the *field*, not the particle count or the array length. Why does Unity validate job fields at `Schedule` time rather than discovering the problem in `Execute`?
- Why is a length-1 array, parked at `(1e9, 1e9)`, preferable to either passing a zero-length slice or branching on `useBoundaryParticles` inside every pass?
- The parked position is far outside the domain so it can never fall within `h` of a fluid particle. What would the density field look like if it were parked at the origin instead?
- `Awake()` calls `ParkDisabledBoundaryArray()` before calibration, and `BoundaryView()` self-heals as a fallback. Why is the self-heal necessary when the ordering is already correct — what class of future edit does it defend against?
- This single unconstructed array produced the symptom "one particle at the centre." Reconstruct the chain: exception in `Awake` → exception each `Update` → which pass never ran → what the render buffer contained → how N instances all drew at one point.

## Snippet 8 — What deliberately stays serial

```csharp
/// These are still single-threaded Burst methods rather than jobs. They are O(N)
/// with a tiny constant, and the time-step one runs before the solver each step, so
/// parallelising them would cost more in scheduling than it saves. A two-stage
/// reduction job would be the move if that ever changes.
[BurstCompile]
public static float ComputeStableTimeStep(in ParticleState state, in SolverParams p, float cflFactor)
{
    for (int i = 0; i < state.Count; i++) { /* max speed, max accel */ }
}
```

```csharp
float dt = Mathf.Clamp(
    SPHSolver.ComputeStableTimeStep(state, solverParams, cflFactor),
    minTimeStep, maxTimeStep);

dt = Mathf.Min(dt, timeAccumulator);
RunIntegratePass(dt);
```

**Explain:**
- `ComputeStableTimeStep` is the only read of `max‖v‖` and `max‖a‖` in the whole loop. Why does its **latency**, not its throughput, decide whether it is worth parallelising?
- Sketch the two-stage reduction you would write if `N` grew by 100×. What is the intermediate array, and what does each stage reduce?
- `IntegrateJob` is scheduled separately from the force passes, with a `.Complete()` in between. Which value forces that split, and why can't `dt` be computed one step ahead instead?
- `viscosity.Complete()`, `IntegrateJob … .Complete()` and `RepackRenderBufferJob … .Complete()` are three separate sync points per frame. What is the main thread doing during each wait, and what is it *not* doing? Which of the three could be overlapped with the next frame, and what would that require?
- The Done criterion is "uses all available CPU cores" and "5,000+ particles at interactive rates." Which of these does the code make true, and which one can only be established by running the Profiler? Why is the distinction worth stating in the commit message?
