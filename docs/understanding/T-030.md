# T-030 Understanding — 2D Spatial Hash Key Generation

Explain each snippet in your own words. Focus on **why** each choice was made and what breaks without it.

> **This task's Guide and the T-023 note disagree.** The Guide mandates the prime-multiplier hash. The T-023 note says hashing exists for *unbounded* domains, "pays for that with collisions", and measured slowest of five methods on a *bounded* one — which is what this project has. Both schemes are implemented; the build defaults to the direct index. Section 2 is about that decision.

## Snippet 1 — Cell coordinate and grid geometry

```hlsl
int2 CellCoordOf(float2 position)
{
    return (int2)floor((position - _GridOrigin) / _CellSize);
}
```

```csharp
CellSize = math.max(0.0001f, parameters.smoothingLength);

float margin = parameters.smoothingLength * 1.01f;
float2 half = parameters.boxHalfSize + new float2(margin, margin);
float2 size = half * 2f;

GridOrigin = parameters.boxCenter - half;
GridCols = math.max(1, (int)math.ceil(size.x / CellSize));
GridRows = math.max(1, (int)math.ceil(size.y / CellSize));
```

**Explain:**

- What does the 3×3 query guarantee only when cell size is `>= h`? Construct the failure case for a cell size slightly *less* than `h`.
- The domain is the container plus `h` of margin on every side. Why does the grid need to extend past the walls at all, given that boundary particles are static and never inside the fluid?
- The margin is multiplied by `1.01`. It is not exactly `h`. Why the extra 1%?
- This geometry mirrors `SPH2D.RebuildNeighbors`. Why does it matter that the CPU grid and the GPU grid agree on origin and cell size, rather than each being internally consistent?
- Why `floor` before casting to `int2`, rather than casting straight from the division?

## Snippet 2 — Two key schemes, one function

```hlsl
uint KeyForCell(int2 cell)
{
    if (_KeyMode == 1u)
    {
        uint x = (uint)cell.x * 73856093u;
        uint y = (uint)cell.y * 19349663u;
        return (x ^ y) % _HashTableSize;
    }

    int cx = clamp(cell.x, 0, (int)_GridCols - 1);
    int cy = clamp(cell.y, 0, (int)_GridRows - 1);
    return (uint)(cy * (int)_GridCols + cx);
}
```

```
DirectIndex  buckets=441  distinctCells=94  occupied=94  maxOcc=7
SpatialHash  buckets=801  distinctCells=94  occupied=89  maxOcc=11
```

**Explain:**
- In the direct-index mode, `occupied == distinctCells` exactly. What property does that mean the key function has, and which mode does *not* have it?
- In the hash mode, 94 distinct cells map to only 89 buckets. Where did the other 5 go, and does any particle become unfindable because of it?
- The direct mode uses **more** buckets than distinct cells (441 vs 94). Is that waste? What is the alternative — could you allocate only the occupied cells?
- The hash table is `2N+1 = 801` buckets against the grid's 441. Intuition says a bigger table means fewer candidates per query. Explain why that intuition is wrong **here**, using the fact that cell size = `h`.
- If particles were clustered into one corner of a very large box, would the comparison still favour the direct index? Explain what changes.
- `h` is derived as `2.2 × spacing`, and spacing is derived from `N` and the spawn area. Substitute those to show that the direct grid's cell count is `O(N)` — i.e. that the direct index does not scale worse in memory either.

## Snippet 3 — The hash itself

```hlsl
uint x = (uint)cell.x * 73856093u;
uint y = (uint)cell.y * 19349663u;
return (x ^ y) % _HashTableSize;
```

**Explain:**
- Why XOR rather than `+`? What would adding do to two cell coordinates that are numerically similar, or that share a common factor?
- Why primes specifically? What artifact appears if you hash a regular lattice — which is exactly what a spawn grid produces — with a small composite multiplier?
- `(uint)cell.x` on a negative `int` wraps to a huge value. Is that a bug? What property of the hash does it affect, and what does it *not* affect?
- The Guide uses the literal constants `73856093` and `19349663`. Are those special, or arbitrary odd primes? What would you have to check before choosing your own?
- `% _HashTableSize` with a non-power-of-two table costs a real integer division. Why not pick `tableSize = 2^k` and use `& (tableSize - 1)`? Name one thing you would lose.
- The whole point of a sparse hash is fitting an unbounded domain into a fixed table. What is the load factor here, and is it the right way to judge this table?

## Snippet 4 — Why the cell coordinate is stored too

```hlsl
_CellCoords[i] = cell;
_CellKeys[i] = KeyForCell(cell);
```

```hlsl
/// The coordinate is kept as well as the key because a hashed bucket cannot be
/// inverted: a neighbour query has to reject candidates whose cell is not
/// actually adjacent.
```

**Explain:**
- A hash is a function `cell → bucket`. Why can it not be inverted to give `bucket → cell`?
- In the **direct** mode the key *is* the cell, one-to-one. Is storing `_CellCoords` redundant there? Argue both directions.
- Suppose a neighbour query scanned 9 buckets and never checked cell coordinates — only the distance test. Would it still be *correct*? Would the answer differ between the two modes?
- The distance test alone is enough for correctness. So what is the cell check actually saving, and how much of the 3×3 scan does it reject?
- T-031 will sort by `_CellKeys`. Why does the sort not need `_CellCoords` at all?

## Snippet 5 — Verification

```
[T030] mode=DirectIndex n=400 buckets=441 distinctCells=94 occupied=94 maxOcc=7
       keyMismatch=0 cellMismatch=0 outOfRange=0 summed=400 ok=True
[T030] mode=SpatialHash n=400 buckets=801 distinctCells=94 occupied=89 maxOcc=11
       keyMismatch=0 cellMismatch=0 outOfRange=0 summed=400 ok=True
```

**Explain:**
- The test recomputes every key on the CPU and compares **bit for bit** rather than approximately. Why is exact comparison the right choice here, when every physics check in T-027/T-028 used tolerances?
- What does `summed == n` establish, and why is that the concrete form of "no particles are lost or duplicated"?
- `outOfRange == 0` checks `key < bucketCount`. What would a key outside that range do at T-031, and why is it important to catch it here rather than there?
- The test reads particle positions back from the GPU and keys the CPU recomputation from *those*, rather than from the original CPU positions. Why does that make the comparison strictly stronger?
- `distinctCells` is computed on the CPU from the cell coordinates. What would it mean if `occupied > distinctCells`? Can that happen?
- `maxOcc` is 7 for the direct index and 11 for the hash. Does a higher `maxOcc` change the *result* of a query, or only its cost? Which one, and under what circumstances does it become a correctness problem?
