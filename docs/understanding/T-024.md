## Snippet 1 — The constraint that forced the refactor

Unity's Burst documentation states:

> *"Burst works on a subset of .NET that doesn't let you use any managed objects or reference types in your code (classes in C#)."*

> *"Burst doesn't support managed arrays. Instead, use a native container such as `NativeArray<T>`."*

Before this task the solver used:

```csharp
private List<int>[] neighbors;        // managed array OF managed objects
private Particle2D[] particles;       // managed array
private Vector2[] boundaryParticles;  // managed array
```

**Explain:**
- `List<int>[]` is disqualified twice over. State both reasons.
- A `Particle2D[]` is an array of *structs*, not classes. Why is it still rejected?
- What does Burst do with a managed array that makes it impossible to compile? (Think about what the GC needs to know about references.)
- `Particle2D` is a struct with only `float2` and `float` fields, and it survives the transition unchanged. Why is a struct of blittable fields acceptable where an array of them is not?

## Snippet 2 — Why `[BurstCompile]` on the kernels alone would not help

You *could* have done this:

```csharp

{
    [BurstCompile]
    public static float Poly6Kernel(float r2, float h2, float poly6Const) { ... }
}
```

...and called it from the existing managed loops. The docs confirm it works: *"You can call Burst-compiled methods direct from managed code"*, with an IL post-processing step rewriting the call into a function pointer.

**Explain:**
- Why would this likely make the simulation **slower** rather than faster?
- What three overheads remain in the surrounding managed loop even though the kernel itself is compiled?
- Burst can inline the kernel into its caller. Under the leaf-function scheme, which side of the boundary does the call sit on, and what does that prevent?
- State the general rule this illustrates about where `[BurstCompile]` has to go to pay off.

## Snippet 7 — Memory ownership

```csharp
private void Awake()
{
    particles = new NativeArray<Particle2D>(TotalParticles, Allocator.Persistent);
    viscosityForces = new NativeArray<float2>(TotalParticles, Allocator.Persistent);
    ...
}

private void OnDestroy()
{
    if (particles.IsCreated) particles.Dispose();
    if (viscosityForces.IsCreated) viscosityForces.Dispose();
    if (boundaryParticles.IsCreated) boundaryParticles.Dispose();
    grid.Dispose();
}
```

```csharp
private void EnsureCellStorage()
{
    if (!packedCell.IsCreated || packedCapacity < totalCount)
    {
        DisposeIfCreated(packedCell);
        packedCapacity = math.max(1, totalCount);
        packedCell = new NativeArray<int>(packedCapacity, Alloc);
    }
}
```

**Explain:**
- `NativeArray` is unmanaged memory, so it is not garbage collected. What does that mean for the `Dispose()` calls, and what are the consequences of forgetting them?
- `Allocator.Persistent` vs `Allocator.Temp` / `TempJob`: why is `Persistent` correct for arrays that live for the whole session? What are the other allocators for?
- The grid grows its arrays only when capacity is insufficient (`< totalCount`), whereas `EnsureNeighborStartStorage` clears them in the else branch. Why do those two cases need different handling?
- `Awake` calls `BuildSolverParams()` **twice** — before mass calibration and again after boundary particles are spawned. Why is the first call necessary at all, given the second overwrites it?
- `BoundaryView()` returns a length-0 `NativeArray` when the toggle is off rather than reallocating. What does that buy, and which two places must agree that it is empty?
