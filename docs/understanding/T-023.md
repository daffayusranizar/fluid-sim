## Snippet 1 — Cell size and grid domain

```csharp
cellSize = Mathf.Max(0.0001f, smoothingLength);
cols = Mathf.Max(1, Mathf.CeilToInt(domainSize.x / cellSize));
rows = Mathf.Max(1, Mathf.CeilToInt(domainSize.y / cellSize));
cellCount = cols * rows;
origin = domainOrigin;
```

```csharp
// in SPH2D.FindNeighbors()
float margin = smoothingLength * 1.01f;
Vector2 domainSize = boxSize + new Vector2(2f * margin, 2f * margin);
Vector2 domainOrigin = (Vector2)transform.position - domainSize * 0.5f;
```

**Explain:**
- Why is the cell size set to **exactly** the smoothing length, rather than something smaller?
- Measurements (Ihmsen et al. 2011) show `0.5h` cells test *fewer* particle pairs (15.5M vs 25M) yet run *slower* (39.6ms vs 26.6ms). Explain why.
- Why does the grid domain extend `h` beyond the container on every side? What would break if it were exactly `boxSize`?
- **Correctness question:** the 3×3 query is only guaranteed to find every neighbour if cell size is **≥ `h`**. Construct a case with cell size slightly *less* than `h` where two particles are within `h` of each other but land two cells apart. Why does using exactly `h` rule this out?
- `cols` uses `CeilToInt`, so the grid covers `cols × cellSize ≥ domainSize`. Why is over-covering harmless while under-covering would be a bug?

## Snippet 2 — The counting sort

```csharp
// 2. Count particles per cell (cellStart doubles as the counter here)
System.Array.Clear(cellStart, 0, cellCount);
for (int p = 0; p < totalCount; p++)
{
    cellStart[packedCell[p]]++;
}

// 3. Exclusive prefix sum
int running = 0;
for (int c = 0; c < cellCount; c++)
{
    int count = cellStart[c];
    cellStart[c] = running;
    cellCursor[c] = running;
    running += count;
}

// 4. Scatter
for (int p = 0; p < totalCount; p++)
{
    int c = packedCell[p];
    sortedByCell[cellCursor[c]++] = p;
}
```

```csharp
private int CellEnd(int cell)
{
    return cell + 1 < cellCount ? cellStart[cell + 1] : totalCount;
}
```

**Explain:**
- Describe what each of the three passes produces. What is in `cellStart` after pass 2, and what is in it after pass 3 — and why can the same array hold both?
- Pass 3 reads `count` *before* overwriting `cellStart[c]`. What would break if the order were reversed?
- Why does cell `c`'s run end exactly where cell `c + 1`'s begins? (This is what makes `CellEnd` work without storing an explicit end array.)
- What range does an **empty** cell produce, and why is that automatically correct?
- Why is this layout better than `List<int>[]` buckets, one list per cell? Give at least two reasons.
- This is the same algorithm as T-031's GPU count sort and prefix scan. Why does that make it worth learning here rather than later?

## Snippet 3 — The 3×3 query

```csharp
int cx = ColumnOf(posI.x);

}
```

**Explain:**
- Why 9 cells in 2D? What is the equivalent count in 3D, and why?
- Out-of-range cells are **skipped**, not clamped. Explain what would go wrong if you clamped the cell coordinates instead. (Think about a particle in the bottom-left corner.)
- The radius test is `sqrMagnitude < radiusSq` rather than `Distance(...) < h`. Why does that matter at this scale, and how much work does it save?
- The neighbour sets produced here are **identical** to the old brute-force result. Why is that guaranteed rather than merely likely?
- Compare the loop shape here with the old brute-force `for j in all particles`. What is the complexity of each, and what does the inner loop now iterate over?

## Snippet 4 — Packed indices: fluid and boundary in one grid

```csharp
// fluid
for (int i = 0; i < fluidCount; i++)
{
    packedCell[i] = CellOf(fluid[i].position);
}

// boundary
for (int b = 0; b < boundaryCount; b++)
{
    packedCell[fluidCount + b] = CellOf(boundary[b]);
}
```

```csharp
if (p < fluidCount)
{
    if (p == i) continue;

{
    int b = p - fluidCount;
```

**Explain:**
- Why do boundary particles share the same grid rather than getting a second one, or staying as a brute-force `O(N × B)` loop?

- The query splits candidates by `p < fluidCount`. Why is this a better arrangement than two separate 3×3 traversals (one for fluid, one for boundary)?
- Boundary particles never move, so their cell membership is fixed. What optimisation does that permit, and why is it *not* worth doing at this particle count?

## Snippet 5 — Storage reuse

```csharp
private void EnsureStorage()
{
    if (packedCell == null || packedCell.Length < totalCount)
    {
        packedCell = new int[Mathf.Max(1, totalCount)];
        sortedByCell = new int[Mathf.Max(1, totalCount)];
    }

    if (cellStart == null || cellStart.Length < cellCount)
    {
        cellStart = new int[cellCount];
        cellCursor = new int[cellCount];
    }

    if (FluidNeighbors == null || FluidNeighbors.Length != fluidCount)
    {
        FluidNeighbors = new List<int>[Mathf.Max(1, fluidCount)];
        // ...
    }
}
```

**Explain:**
- `FindNeighbors()` runs **once per substep**, which can be 3+ times per frame. Why does that make allocation behaviour critical?
- `packedCell` reallocates on `< totalCount` (grow-only), while `FluidNeighbors` reallocates on `!= fluidCount` (any change). Why the different policies?
- The neighbour lists are `Clear()`ed then refilled each query rather than recreated. What does that cost, and what does it avoid?
- The old brute-force code did `neighbors = new List<int>[n]` **every call**. Why was that acceptable at 100 particles but a problem at 5,000?
