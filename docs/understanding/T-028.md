## Snippet 2 — The trap: gradient functions have no `r >= h` early-out

```hlsl
// NOTE: unlike the value kernels above, the gradient functions have no r >= h
// early-out -- matching SPHMath.cs, where SpikyPow2GradientMagnitude returns a
// negative (h - r) beyond h.
float SpikyPow2GradientMagnitude(float r, float h, float k)
{
    return k * (h - r);
}
```

```hlsl
float2 rVec = posI - _ParticlesIn[j].position;
float r2 = dot(rVec, rVec);

// The explicit r < h test that the neighbour grid normally provides.
if (r2 >= h2 || r2 <= 0.0) continue;
```

**Explain:**
- Compare with `SpikyPow2Kernel`, which *does* start with `if (r >= h) return 0.0;`. Why does the value kernel need that guard but the gradient kernel not have one?
- The CPU calls `SpikyPow2GradientMagnitude` without any radius test. What guarantees `r < h` there, and why does that guarantee disappear in a brute-force GPU loop?
- What does `k * (h - r)` evaluate to for a particle at `r = 3h`? What sign is the resulting contribution, and what does that do to a particle that should not feel any force from that neighbour?
- `SpikyPow3GradientMagnitude` is `k * (h - r)^2`, which is *positive* even past `h`. Is that bug better or worse than the SpikyPow2 case? Why is "it has the right sign" not a defence?
- The boundary loop has the same requirement. Why is it easy to remember the guard in the fluid loop and forget it in the boundary loop?
- A mutation test removed this guard and the force came out as `±1e9` against the CPU's `1e6`. What does that tell you about whether this bug is easy to spot by eye in a running simulation?

## Snippet 3 — Two force channels with different gradient shapes

```hlsl
float sharedPressure = (_Pressure[i] + _Pressure[j]) * 0.5;
accumulated += dir * (_ParticleMass
                      * SpikyPow2GradientMagnitude(r, h, _SpikyPow2GradConst)
                      * sharedPressure / otherDensity);
```

```hlsl
float sharedNearPressure = (_NearPressure[i] + _NearPressure[j]) * 0.5;
accumulated += dir * (_ParticleMass
                      * SpikyPow3GradientMagnitude(r, h, _SpikyPow3GradConst)
                      * sharedNearPressure / otherNearDensity);
```

**Explain:**
- Both terms have the shape `dir * mass * gradW * sharedPressure / otherDensity`. Why is the pressure *averaged* rather than taken from either particle alone?
- The main gradient is linear in `(h - r)`; the near gradient is quadratic. The invariant table says the near/main ratio must fall from ~2.5× at `r = 0` to 0 at `r = h`. Verify that from these two expressions.
- Suppose both channels used the quadratic gradient, differing only by a constant. Would the near channel still prevent particle pairing? Why not?
- `dir` is `(posI - posJ) / r`, pointing from `j` toward `i`. If it were negated, would the fluid collapse or explode? Which sign of `sharedPressure` makes that question non-trivial?
- The main channel can be attractive (negative pressure). The near channel cannot. What stops the attractive regime from collapsing the fluid entirely?
- `otherDensity` is the *neighbour's* density in the divisor, not this particle's. Why is the symmetrised form written that way?

## Snippet 4 — The boundary push is unconditionally clamped

```hlsl
// Mirroring copies this particle's own pressure, and that value is often
// negative near a wall where density is below rest. A mirrored negative
// pressure would make the boundary attractive, so it is clamped --
// unconditionally, and independently of _ClampPressurePositive, exactly as the
// CPU does.
float boundaryPressure = max(0.0, _Pressure[i]);
```

```hlsl
accumulated += dir * (_BoundaryVolume * boundaryPressure
                      * SpikyPow2GradientMagnitude(r, h, _SpikyPow2GradConst));
```

**Explain:**
- There are now **two** different clamps in the solver: `TaitPressure(..., clampPositive)` and this `max(0, _Pressure[i])`. Why does the second one exist even when `clampPressurePositive` is `false`?
- The T-024 supplement says clamping the main channel conflicts with the near channel and must stay off. Why does that argument *not* apply to the boundary clamp?
- Compare the terms: the fluid force carries `_ParticleMass` and divides by `otherDensity`; the boundary force carries `_BoundaryVolume` and divides by nothing. Where does the missing divisor go?
- Note the phrase "the wall may push but never pull". What physical behaviour does the unconditional clamp enforce, and what happens at a free surface where `_Pressure[i]` is legitimately negative?
- If a particle's own pressure is negative, this term contributes zero. Does that mean the wall stops acting on it? What else is still acting on it? (Think about what T-020 added besides pressure.)

## Snippet 5 — Viscosity is XSPH, not a Laplacian

```hlsl
// XSPH: Poly6 is a weight on the velocity difference, not a Laplacian.
// Being non-negative everywhere it can only pull this velocity toward
// its neighbours', so there is no sign to get wrong and no way for the
// term to add energy. It also needs no square root.
viscForce += (_ParticlesIn[j].velocity - velI)
             * Poly6Kernel(r2, _SmoothingLengthSq, _Poly6Const);
```

```csharp
shader.SetFloat("_Poly6Const", parameters.poly6Const);
shader.SetFloat("_SmoothingLengthSq", parameters.smoothingLengthSq);
```

**Explain:**
- The TASKS.md Guide says "Viscosity Laplacian". What is the property of a Laplacian that makes Müller's formulation risky, and why does a non-negative *weight* not share it?
- `Poly6Kernel` takes `r2` and `h2`, not `r` and `h`. Where else in the solver is that same choice made, and what does it save?
- State what `viscForce` is measuring in words. Is it a force, or a velocity blend that gets scaled into a force?
- `_Force[i] += viscForce * _Viscosity;` while `_Force[i] = accumulated;` in the previous kernel. Which of the two is an accumulation, and why does that matter for dispatch ordering?
- Viscosity is described as "the only dissipative term". What happens to the fluid over time if it is dropped — and why does that present as a *visual* problem rather than a crash or a NaN?
- The verification for this task initially reported `viscosityForce = 0` on both CPU and GPU. Why was that a vacuous pass rather than a real one, and what did the fix have to change in the *test* (not the shader)?

## Snippet 7 — Integration and the two guards

```hlsl
if (particleDensity <= 0.0001)
{
    _ParticlesOut[i] = _ParticlesIn[i];
    return;
}
```

```hlsl
float2 acceleration = _Force[i] / particleDensity + _Gravity;
float2 v = p.velocity + acceleration * _DeltaTime;
float2 pos = p.position + v * _DeltaTime;
```

**Explain:**
- The CPU guard is `if (particleDensity <= 0.0001f) return;` and it integrates *in place*. Why does the GPU have to write `_ParticlesIn[i]` to `_ParticlesOut[i]` instead of just returning?
- What exactly is being avoided by that guard — division by zero, or something subtler? What would a particle with no neighbours do without it?
- Velocity is updated **before** position, and position uses the *new* velocity. Name the integrator, and say what would differ if position used the old velocity.
- The wall clamp mutates both `pos` and `v`. Why does the position need clamping at all, when boundary particles already push the fluid away?
- `v.x *= -_CollisionDamping` with damping `0.5` means a bounce loses half its speed. How many bounces until the wall term is effectively invisible, and why does that make the clamp a safety net rather than the wall model?
- The tests compare `velocityAfter` and a separate `positionDelta` rather than just `positionAfter`. Why is comparing absolute position a weak test for an integration bug?
