# T-029 Understanding — CPU-GPU Pipeline Integration

Explain each snippet in your own words. Focus on **why** each choice was made and what breaks without it.

> This task contains the project's one genuine architectural fork: "zero CPU readback" versus T-021's adaptive step, since the CFL limit needs `max‖v‖` and `max‖a‖`, which are CPU-side numbers. The choice made here is **(a) GPU reduction plus one small asynchronous readback consumed a frame late**, and it is recorded as GPU Port Decision #4.

## Snippet 1 — Ping-pong, and why one buffer cannot work

```csharp
private readonly ComputeBuffer[] particleBuffers = new ComputeBuffer[2];
private int current;

private ComputeBuffer ParticlesIn  => particleBuffers[current];
private ComputeBuffer ParticlesOut => particleBuffers[1 - current];
```

```csharp
DispatchIntegrate(dt);   // reads ParticlesIn, writes ParticlesOut
SwapParticles();         // the buffer just written becomes the current one
```

**Explain:**
- `Integrate` reads `ParticlesIn[i]` and writes `ParticlesOut[i]`. If both names referred to the same buffer, is that a race? Each thread only touches index `i`, so argue it carefully.
- Given your answer above, why is a second buffer still the right call? Consider what happens the moment any kernel needs a *neighbour's* newly integrated position.
- `SwapParticles()` flips an index rather than copying data. What does that cost, and what would copying cost at 10,000 particles × 60 fps?
- After N steps, which buffer holds the answer? How does `Readback` know which one to read?
- The probe self test calls `SwapParticles()` after `DispatchProbe`. Why does that have to be there, and what would the test report if it were missing?

## Snippet 2 — One step, in order

```csharp
public void StepOnce(float dt)
{
    DispatchDensityPressure();
    DispatchForces();
    DispatchReduceExtremes();
    DispatchIntegrate(dt);
    SwapParticles();
}
```

**Explain:**
- The reduction runs **after** forces and **before** integration. Why that exact position? What state does it need, and why must it be pre-integration?
- The CPU measures the same quantities in `Update()` between `SolveStep()` and `RunIntegratePass(dt)`. What does that tell you about where the reduction belongs?
- If the reduction moved to after `DispatchIntegrate`, would the numbers be wrong, or merely different? Which of the two inputs would change and which would not?
- `DispatchIntegrate` reads `_Force`, which `DispatchForces` wrote. What guarantees that ordering on the GPU? On the CPU this was a `JobHandle` — name the replacement.
- Nothing in this method reads back to the CPU. Where in the whole method is there an opportunity for a hidden stall, and how is it avoided?

## Snippet 3 — Reducing on the GPU with integer atomics

```hlsl
float speed = length(_ParticlesIn[i].velocity);
InterlockedMax(_Extremes[0], asuint(speed));

float d = _Density[i];
if (d > 0.0001)
{
    float2 a = _Force[i] / d + _Gravity;
    InterlockedMax(_Extremes[1], asuint(length(a)));
}
```

**Explain:**
- HLSL has no atomic operation on `float`. Explain why `asuint` makes this work: what property must the value have for unsigned integer ordering to match float ordering?
- Which of these two values is a magnitude, and what would happen if you tried the same trick on a signed quantity like a single velocity component?
- `_Extremes` is cleared by a separate one-thread `ClearExtremes` dispatch. Why can this not be done by clearing inside `ReduceExtremes`?
- What would a NaN in a velocity do to this reduction, and why does that make the reduction an unreliable *health check* even though it is a reliable max?
- The `if (d > 0.0001)` guard mirrors the CPU. What would happen without it, and why is "the result would be infinite" not caught by `max`?
- A full two-stage GPU reduction (per-group partials, then a final pass) is the textbook approach. Why is a single group plus atomics acceptable here, and at what particle count would it stop being acceptable?

## Snippet 4 — The decision: async readback versus a fixed step

```csharp
public void RequestExtremesReadback()
{
    if (!ready || extremesPending) return;
    extremesPending = true;
    extremesRequest = AsyncGPUReadback.Request(extremes);
}

private void Update() => PollExtremesReadback();

public void PollExtremesReadback()
{
    if (!extremesPending || !extremesRequest.done) return;
    ConsumeExtremes();
}
```

```csharp
if (!extremesPending) return;
extremesRequest.WaitForCompletion();
ConsumeExtremes();
```

**Explain:**
- The task forbids the step "silently becoming fixed". What exactly would be lost if option (c) were taken — describe the user-visible consequence, not the code change.
- `RequestExtremesReadback` is called once per **frame**, not once per step. Why? What would happen if a frame with `maxSubSteps` substeps issued one request per step?
- The `if (extremesPending) return;` guard is the whole anti-backlog mechanism. What would a queue of pending readbacks do to latency and memory?
- On `hasError`, `ConsumeExtremes` keeps the previous estimate rather than falling back to zero. Work out what a zero `maxSpeed` would do to `dt` in the CFL formula — why is "keep the old value" the safe failure?
- The readback is **poll-based**, not callback-based, for a specific testability reason. What is it?
- The values are one frame old. Argue why this is not a behaviour change compared to the CPU solver, using what the CPU does *today* in `SPH2D.Update`.
- `WaitForCompletion` exists for tests. Why must production never call it?

## Snippet 5 — The driver owns time

```csharp
accumulator += Time.deltaTime;
int steps = 0;

while (accumulator > 0f && steps < maxSubSteps)
{
    float dt = Mathf.Clamp(StableTimeStep(compute.LastMaxSpeed, compute.LastMaxAccel),
                           minTimeStep, maxTimeStep);
    dt = Mathf.Min(dt, accumulator);
    compute.StepOnce(dt);
    accumulator -= dt;
    steps++;
}

accumulator = 0f;
```

```csharp
private float StableTimeStep(float maxSpeed, float maxAccel)
{
    SolverParams p = source.Parameters;
    float soundSpeed = Mathf.Sqrt(Mathf.Max(0f, p.stiffness));
    float dtCfl = cflFactor * p.smoothingLength / (maxSpeed + soundSpeed + 0.0001f);
    float dtAcc = maxAccel > 0.0001f ? cflFactor * Mathf.Sqrt(p.smoothingLength / maxAccel)
                                     : float.MaxValue;
    return Mathf.Min(dtCfl, dtAcc);
}
```

**Explain:**
- `SPHCompute` owns one step; `SPHComputeSimulation` owns time. Why is that a useful split rather than putting the loop in `SPHCompute`?
- `dt = Mathf.Min(dt, accumulator)` — what would happen without it? What does the simulation do if a step overshoots the remaining frame budget?
- `accumulator = 0f` after the loop discards the backlog. Why is that the right call, and what does the alternative ("spiral of death") look like?
- Compare `StableTimeStep` with `SPHSolver.ComputeStableTimeStep`. Why do they have to stay identical, and what is the risk of having the formula written out twice?
- Before the first readback completes, `LastMaxSpeed` and `LastMaxAccel` are both 0. Compute the resulting `dt` and say whether that is safe for a fluid starting at rest.
- Sound speed is `sqrt(stiffness)` because `p = k(ρ − ρ₀)` gives `dp/dρ = k`. A stiffer fluid therefore forces a smaller step. Where in this method does that show up?

## Snippet 6 — What still touches the CPU

```csharp
source.solveOnCpu = false;

compute.UploadBoundary(source.BoundaryParticles);
compute.UploadParameters(source.Parameters);
```

```csharp
// NativeArray(T[], Allocator) copies INTO native memory, so the readback
// lands in the native buffer and has to be copied back out explicitly.
var native = new NativeArray<Particle2D>(activeCount, Allocator.Temp);
compute.Readback(native);
native.CopyTo(snapshot);
native.Dispose();
```

**Explain:**
- Three things still come from the CPU: the spawn, the boundary set, and the parameter block. Why is it correct that these stay CPU-side rather than being ported?
- `source.solveOnCpu = false` exists so the Burst solver does not advance the same particles. What would you observe if this flag were forgotten — two fluids, a corrupted one, or a crash?
- `SPH2D.Awake` now calls `RunRepack()` at the end. Why was that necessary once a GPU simulation seeds from `Particles` in `Start()`?
- The gizmo snapshot is a synchronous readback of the entire particle buffer, throttled to every N frames. Is this a violation of "zero CPU readback during simulation"? Justify your answer using the task's own wording.
- `NativeArray(T[], Allocator)` looks like it aliases the managed array. What does it actually do, and what was the bug when this was written the obvious-looking way?
- `OnDestroy` sets `solveOnCpu = true`. Why is that more than tidiness?
